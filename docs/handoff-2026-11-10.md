## 剩余四项：目标、入口与验收

### A. 拖入小面板与移出/取消后收起

用户期望：拖动文件靠近顶部时出现更小的接收版本，少占屏幕；仍按着鼠标移出该区域时就消失；取消后不能残留。用户说“我们有做一个小一点的版本”，先审计复用。口述“这个键盘还在”保留原话，目前不能认定指面板、输入焦点或系统键盘，复现时具体确认。

入口：`Clipio/CollectionAccessController.swift` 的 `handle`、`updateEntry`、`openCollection`、`CollectionEntryDropView`；`Clipio/FloatingPanel.swift` 的拖动保护、打开/关闭；`Clipio/Observables/Popup.swift`。

当前事实：已有持久化的 compact 入口/drop host，拖动时尺寸约 220×52，位于刘海下方；靠近 820×260 顶部区域会 `openCollection(forDrag: true)` 打开完整 shelf。`openedForDrag`、`showingDrag` 和鼠标释放延迟负责状态。当前没有完整的“仍按住但移出区域就收起”逻辑；不能只修改鼠标松开后的计时。底层还有 `FloatingPanel` 自己的 mouse-up 监视器，已有 generation 防止旧延迟覆盖下一次拖动，修改时保持一致。

验收：靠近出现小接收界面；按住移出收起；再进入可重新出现；取消不残留；成功落放、文件/卡片保留规则及手动打开完整收集区不受影响。多屏拖动展开后不跟随是已知后续项，别把同屏结果冒充多屏通过。

### B. Liquid Glass 仍未达到用户期望

用户明确否定当前观感：“还是没有做到我们之前的样子”。状态是**视觉未验收**，不能以使用原生 API 或设置能切换代替通过。用户会在其他 section 安排 UI agent，不能在本会话自行派发。

入口：`Clipio/Views/VisualEffectView.swift` 的 `ShelfGlassSurface`、`ContentView.swift` 的背景/动画、`FloatingGlassStyle.swift`、`CardItemView.swift` 的背景、`CollectionShelfView.swift`、`FloatingPanel.swift`；外观选项在 `AppearanceSettingsPane.swift` 和 `Defaults.Keys+Names.swift`。

当前实现：共享原生 `.regular` / `.clear`（跟随系统/更通透），系统 Reduce Transparency 优先；没有通过全窗 alpha 淡化文字。两档选项存在且可操作，不等于效果达标。

接手先确定用户之前认可的样子。`Designs/explorations/2026-11-09-liquid-glass/` 与 `2026-11-09-style-study/` 是历史讨论素材，**不等于已认可的目标**。已确认继续用系统标准字体及原版香蕉装小马图标，不要重新开启这两项选择。

验收：实际运行包与用户确认的参考对比；同时看浅深色、系统透明度、文字/选中态可读性。完成后给用户集中体验，不用逐个小改让用户反复编译。

### C. Tab 切换时顶部 Menu Bar 晃动

用户反馈顶部 Menu Bar 动来动去，希望位置/尺寸稳定。用户怀疑图标大小不同，仅为假设，原因未核实。

入口：`Clipio/Views/ListHeaderView.swift` 的 `ShelfMode.symbol` 与搜索框 `.id(shelfMode)`；`CollectionItem.swift` 的 `ShelfMode`；`AppState.switchShelf`、`Popup` 的 Tab 拦截；`AppDelegate.swift` 的 `statusItem`、`synchronizeMenuIconText`、`updateStatusItemAppearance`；独立入口也在 `CollectionAccessController`。

先在运行包中区分系统菜单栏图标、独立收集入口与面板内切换图标。面板内图标已有固定 frame（toolbarControlSize），所以不能仅凭名字认定“补固定宽度即可”。

验收：反复 Tab，顶部与相邻菜单栏项目无可见左右跳动；两种模式、搜索与快捷键仍正常；保留输入法组合输入对 Tab 的使用。

### D. 同批多文件 Stack（新需求，未实施）

用户例子：Finder 一次拖七张图片到框里，希望这一批 stack 在一起，需要时展开/拆散显示七个成员。按**同一次拖入**分组，不是把历史中所有图片合并，也不是生成一张合成图片。

待与用户决定：hover / 点击 / 其他展开方式、折叠时缩略图与数量表达、展开布局、单项/整组拖出、Pin 是单项还是整组、重启保留与搜索规则。本轮没有替用户选定这些语义，不要在接手时直接实现猜测方案。

入口：`CollectionImporter.collect`、`CollectionAccessController.receivePromises`、`CollectionShelfView` 的 `.onDrop`、`CollectionItem`/`CollectionStore`、`CollectionDragSource`。目前模型是扁平 items、manifest version 1，没有 batch/group 字段。需要按现有批量入口核对整个 drop 的边界；文件 promise 回调可能异步，不能用“相近时间”代替同一批。如果引入持久化分组，保留旧 manifest 的读写/迁移与失败恢复，不能丢历史项。

验收：同次七张进一组、展开仍看到七个独立成员；下一次拖入不混入上一组。后续 Pin、搜索、拖出和重启行为按最终约定核对，并复跑已通过的文件安全场景。

## 不要破坏的文件边界

- `CollectionStore.prepareExport` / `finishExport(operation:)`、`CollectionDragSource`：普通本地项目使用原生 move；Finder/目标应用拥有文件操作，Clipio 不在 copy 回调后删除本地原件。
- 混合 move 批次为 Pin 项准备副本；父目录移动不能连带移走已 Pin 子项（包括未选中的 Pin 子项）。owned 网页图片与本地引用不同。
- 按每项导出 URL 的实际消失核对 move。回调先到时用文件事件监听后续完成；观察 30 分钟后仍不明确则保留卡片，不推断成功。
- 普通本地 move 批次不会向 copy-only 目标静默降级；需要复制/上传时先 Pin。大 Pin 文件夹的混合导出 staging 仍在主线程，属于已知性能项。
- 剪贴板 SwiftData 和收集区 manifest 分开。`~/Library/Application Support/Maccy/Storage.sqlite` 是刻意保留的旧存储路径，不要顺手改名。沙箱实际路径可能带容器前缀。
- 31 个语言表与 pbxproj knownRegions/variant groups 保持一致；新 Swift 文件需手动加入工程。不要仅看源码文件便声称用户能看到某项资源。
